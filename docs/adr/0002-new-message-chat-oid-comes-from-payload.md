# ADR-0002: chat_oid для New-Message Event берётся из payload, а не из Kafka-key

- **Статус:** Accepted
- **Дата:** 2026-10-07
- **Контекст решения:** живая проверка consumer'а против RouteRelay (fastapi-examples, топик `new-messages`); инцидент «каждое событие падало с 404»
- **Связанные материалы:** `GLOSSARY.md` → *New-Message Event*

## Контекст

Consumer читал `chat_oid = key.decode()` — из Kafka-ключа события. На живом топике ключом ляжет **`event_id`**, а `chat_oid` в payload отличается (проверено на обоих записях топика: `key == event_id`, `chat_oid` — другой UUID). В итоге каждый запрос `listeners` уходил на несуществующий чат → 404 → исключение, уведомления не уходили вообще, а сообщение при этом коммитилось (faststream помечает «Processed» и при ошибке).

Ключ продюсера — это транспортная деталь RouteRelay, а не контракт для клиента: документация и openapi её не фиксируют.

## Решение

**Единственный источник `chat_oid` — payload события** (`NewChatMessageSchema.chat_oid`), типизированное зеркало серверного `BaseEvent`. Kafka-key в обработчике не используется и не декодируется.

## Альтернативы

**A. Договориться с RouteRelay, чтобы key = chat_oid** (партиционирование по чату, порядок сообщений внутри чата). Отклонено: cross-repo изменение ради выигрыша, которого у текущего клиента нет — один consumer, FIFO и так гарантирован одной партицией топика; контракт key нигде не зафиксирован.

**B. Оставить key, но валидировать его как chat_oid и фолбэчиться на payload.** Отклонено: две правды вместо одной, лишняя ветка, которую никто не протестирует.

## Последствия

**Плюсы:**

- клиент совместим с любым продюсером: формат key перестал быть источником истины;
- если RouteRelay позже введёт key = chat_oid для компакции по чату — клиент не заметит.

**Минусы / обязательства:**

- порядок сообщений внутри чата клиент не гарантирует (полагается на порядок в партиции) — это уже свойство топика, а не выбора key;
- `event_id` по-прежнему не используется: дедупликации при at-least-once доставке нет (карточка №5).

## Когда пересматривать

Если RouteRelay зафиксирует key как часть контракта (например, введёт партиционирование по чату и заявит это в документации) — решение остаётся в силе, но стоит дополнить `GLOSSARY.md` определением *Kafka Key*.
