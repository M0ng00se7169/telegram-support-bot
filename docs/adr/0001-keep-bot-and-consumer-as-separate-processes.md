# ADR-0001: Бот и Kafka-consumer остаются двумя процессами с общим composition root

- **Статус:** Accepted
- **Дата:** 2026-10-06
- **Контекст решения:** архитектурное ревью 2026-10-06, кандидат №4 «Composition root» (гриллинг: топология)
- **Связанные материалы:** `GLOSSARY.md` → *Composition Root*

## Контекст

Проект собирает **два процесса** из одного пакета `app/`:

1. **TG-бот** — python-telegram-bot (long polling), запуск `python main.py`, деплой `docker_compose/bot.yaml`;
2. **Consumer** — FastStream-подписка на топик `new-messages` RouteRelay, запуск `faststream run --factory consumers.main:get_app`, деплой `docker_compose/consumer.yaml`.

Оба процесса — «клиенты» RouteRelay: ходят в его HTTP API и читают его Kafka-топик. При ревью DI-слоя возникла развилка: слить ли процессы в один (один asyncio-loop, один DI-контейнер, один Docker-сервис) или оставить раздельными.

## Решение

**Процессы НЕ сливать.** Один общий composition root в `containers/` (провайдеры dishka нейтральны к процессу), из которого **каждый процесс собирает свой app-контейнер**. Потребительский скоуп: одно сообщение Kafka / один апдейт Telegram.

Дополнительные зафиксированные решения того же гриллинга (в рамках этого ADR):

- провайдеры — идиоматичный dishka: `yield`-провайдеры для `AsyncClient`/`Bot`, wiring параметрами (без обходных вызовов `self.get_*()`); settings-унификация (django-environ → pydantic-settings) — **вне** объёма этого решения.

## Альтернативы

**B. Слить процессы** (PTB-луп хостит Kafka-брокер): один контейнер и один Docker-сервис, меньше движущихся частей. Отклонено, потому что:

- связный отказ: падение/рестарт consumer'а (ребаланс партиций, `--reload` в dev) роняет бота, и наоборот — сейчас изоляция отказов бесплатна;
- ручная композиция двух asyncio-приложений с разными жизненными циклами (PTB `run_polling` vs FastStream lifespan) — нетривиальный graceful shutdown, отдельная работа;
- для текущего масштаба (2 процесса, один топик) это YAGNI.

## Последствия

**Плюсы:**

- изоляция отказов и независимый рестарт/деплой каждого процесса;
- deployment-файлы (`bot.yaml`, `consumer.yaml`) не меняются;
- бот не тянет Kafka-брокер, consumer не поднимает Telegram-пуллинг — каждый процесс собирает только своё.

**Минусы / обязательства:**

- провайдеры в общем composition root обязаны быть процессо-нейтральными: никаких side effects на импорте и процесс-специфичных зависимостей в общих провайдерах;
- две стартовые обвязки (`main.py`, `consumers/main.py`) дублируют сборку контейнера — допустимая цена, код сборки один.

## Когда пересматривать

Если появится второй adapter (не Telegram) с собственной потребительской логикой или требование единого деплоя — решение можно supersede-нуть новым ADR.
